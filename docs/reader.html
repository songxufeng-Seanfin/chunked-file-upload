大文件分片上传与秒传 · 技术文档

v1.0 · 2026-11-16 · Django 5.2 + Vue 3 + Pillow + SQLite · 22 个自动化测试全部通过

这份文档按「由外向内」的顺序写：先看你打开页面能看见什么，再看一次请求怎么走一圈，然后进到 Django 内部的路由、视图、业务层、数据表，最后才看一行行实现细节。专业术语第一次出现时，都会用大白话解释一遍，读不懂代码也没关系，先记住骨架。

0. 先站远一点看：这个项目到底是什么

一句话：把大文件切成小块分别上传，服务器按编号拼回去；如果服务器上已经有同样的文件，就直接跳过上传；如果传到一半断了，就只补缺的那几块。

「大文件」在这里指几十 MB 到几百 MB 的东西。一次性 POST 上去会遇到三个麻烦：请求太大会被服务器或网关拒绝、网一断就得从头再来、大请求占满连接让别的操作变慢。分片（chunk，把文件按固定大小切开的小块）就是为了解决这三件事。

打开 http://127.0.0.1:8001/ 能亲眼看到四件事：

你点的东西背后发生的事页面上能看到的证据
一键跑全部场景服务端用真实代码跑四个场景统计卡数字变化、事件时间线多出十几条
选一个本地文件浏览器真的切片、并发 POST、请求合并进度条、分片位图从灰变绿
模拟中断 + 续传新任务只补缺片任务标「续传」，本次传输字节明显少
同一个文件传第二次指纹命中档案，0 字节任务标「秒传命中 · 0 字节」

看板从上到下分成：术语卡（分片 / 秒传 / 断点续传）、一键演示按钮区、真实上传区、六张统计卡、文件档案表、上传任务与分片位图、事件时间线、六步流程图。所有表格数据都来自 /api/state/ 这一个 JSON 接口，页面只是把状态画出来。

为什么这个项目没用对象存储（OSS / S3 这类云存储服务）？因为它是用来讲清楚原理的：本地磁盘 + SQLite 就能跑，不注册任何云账号，断网也能演示。文末第 15 节会诚实列出上线前必须补的东西。

2. 第一层：一次点击，请求怎么走一圈

以「选文件 → 开始上传」为例，浏览器和服务端之间实际发生了这些往返：

浏览器                                       Django 服务
   |                                                |
   |-- GET /  -------------------------------------->|  返回 HTML 外壳 + 种下 csrftoken
   |-- GET /api/state/ ---------------------------->|  返回当前统计 / 文件 / 任务 / 事件
   |                                                |
   | [本地] crypto.subtle 算整文件 SHA-256           |
   |-- POST /api/upload/check/ {指纹,大小,分片大小} -->|  查档案 / 查已有分片，建任务
   |<-------------------- {task_id, uploaded:[]} ---|
   |                                                |
   | [本地] File.slice 切第 0、1、2 片，3 路并发      |
   |-- POST /api/upload/chunk/ (multipart #0) ------>|  校验 → 原子落盘 → 记一条事件
   |-- POST /api/upload/chunk/ (multipart #1) ------>|
   |-- POST /api/upload/chunk/ (multipart #2) ------>|
   |<--------------- {result: APPLIED / DUPLICATE} --|
   |                     …… 直到所有片到齐 ……          |
   |                                                |
   |-- POST /api/upload/merge/ {task_id} ----------->|  按序拼接 → 整文件再算一次指纹
   |<------------------ {result: MERGED} -----------|  生成档案 + 缩略图 + 清理临时块
   |-- GET /api/state/ ----------------------------->|  刷新看板

几个之前学过的状态码，在这个项目里对应什么：

状态码白话本项目的触发点
200成功页面、状态接口、检查接口
400参数不合法指纹不是 64 位十六进制、分片大小越界（UploadError 默认 400）
403不认凭证POST 没带 X-CSRFToken（test_csrf_rejects_post_without_token 专门测了）
404找不到合并时 task_id 不存在（清空重来后再点旧任务）
409 / 413冲突 / 太大同一编号带来不同内容、单片超过 16MB
500服务端崩了兜底异常，views.py 会记日志并返回 JSON 错误

同步和异步：页面上的 fetch 都是异步（async），意思是「发出请求后不卡住界面，等结果回来再继续」；await 就是「这一行要等结果」。并发池里三个 worker 同时 await，所以叫并发上传。

把业务逻辑放进 service.py 是本项目最重要的结构决定：一键演示不是「往表里塞假数据」，而是在服务端调用 check_upload → receive_chunk → merge_task 这一模一样的函数（service.py:474 的 run_demo_scenario）。这样演示跑通，等于真实链路跑通。

CSRF 安检口在这里怎么过？页面视图 console() 上有 @ensure_csrf_cookie（views.py:54），Django 会在响应里种下 csrftoken cookie；前端 app.js:41 的 postJSON 和分片上传都把它放进 X-CSRFToken 请求头。浏览器自动带 cookie、手动带头，两边对上才放行。

4. 第三层：四张数据表，各司其职

表一句话职责关键字段
FileRecord「服务器上已经有这份文件」的档案file_hash（唯一）、size、total_chunks、rel_path、thumbnail、ref_count
UploadTask一次上传会话task_id（唯一）、status、bytes_sent、instant、resumed、source
UploadChunk已落盘的某一片file_hash + index（联合唯一）、chunk_hash、rel_path
UploadEvent可观测性流水：每次检查、拦下、合并都记一条event_type、result、chunk_index、detail

一个决定成败的设计：分片挂在 file_hash 上，不挂在 task_id 上

断点续传的本质是「换个会话也能接着传」。如果把分片绑在任务上，刷新页面新建一个 task 后，旧的片就查不到了，只能从头传。本项目让 UploadChunk 以 (file_hash, index) 为身份：

# uploader/models.py:82
class UploadChunk(models.Model):
    file_hash = models.CharField(max_length=64, db_index=True)
    index = models.PositiveIntegerField()
    class Meta:
        constraints = [models.UniqueConstraint(
            fields=["file_hash", "index"], name="uniq_file_chunk_index")]

于是 check_upload() 只要按 file_hash 查一次，就能告诉新任务「0、1 号片已经有了，只补 2、3、4」（service.py:88）。联合唯一约束同时充当并发闸门：两个请求同时写同一片，数据库只会让一个成功，另一个收到 IntegrityError，被 service.py:169 捕获后当作「重复投递」处理。

任务状态是一个很小的状态机（state machine，规定状态只能怎么变）：

uploading ──收齐分片并合并成功──> merged
    │
    └──整文件指纹校验失败──────> failed
check 命中档案 ─────────────────> instant（直接终态，bytes_sent = 0）

FileRecord.ref_count 记录这份档案被秒传命中了多少次，build_state() 里用它算「省下流量」。

5. 第四层：核心链路六步

5.1 算指纹（浏览器，app.js:196）

const whole = await sha256(await picked.value.arrayBuffer());

crypto.subtle.digest("SHA-256", buffer) 返回整文件的 64 位十六进制指纹。白话：给这堆字节拍一张「证件照」，内容变一个字节，照片就完全不同。注意：Web Crypto 只在安全上下文（secure context，HTTPS 或 127.0.0.1 / localhost）可用，所以本地必须用这两个地址访问，不能直接开文件。

5.2 上传前检查（service.py:88）

服务端做三件事：校验参数；自己按 size / chunk_size 算 total_chunks（不信前端报的片数）；查 FileRecord。

FileRecord 里有这个指纹？
    ├─ 有 → 建 instant 任务、bytes_sent=0、ref_count+1、返回 {instant: true}
    └─ 没有 → 查 UploadChunk 里已有哪些编号 → 建 uploading 任务、返回 {uploaded: [...]}

两条分支都会写一条 UploadEvent，所以看板能看到「为什么没传」。

5.3 分片并发（浏览器，app.js:167 / app.js:196）

const worker = async () => {
  while (queue.length) {
    if (interrupted.value) return;
    while (paused.value && !interrupted.value) await sleep(120);
    const index = queue.shift();
    await sendOne(index);
  }
};
await Promise.all(Array.from({length: concurrency}, worker));

这是一个并发池：开 3 个 worker，共享一个待传队列，谁空了就从队列取下一片。暂停只是让 worker 停在 while (paused) 里，不取消正在飞的请求；「模拟中断」则让 worker 不再取新片，已经发出的请求照常落盘——这正是真实断网的样子，也正是续传要处理的情况。

每一片单独算片指纹，连同 task_id、index、文件内容一起放进 FormData POST 出去。

5.4 幂等闸门（服务端，service.py:169）

「幂等」（idempotency）的意思是：同一件事做 100 次，效果和做 1 次一样。分片可能被重传、被并发重复提交，服务端按这个顺序判断：

检查不通过的结果白话
编号越界 / 大小不符REJECTED这不是我要的那一块
片内容与声明的片指纹不符CORRUPT传坏了，不落盘
该 (file_hash, index) 已存在且指纹相同DUPLICATE来过了，跳过，不重复写盘
已存在但指纹不同CONFLICT同编号带了两个不同内容，拒绝覆盖
都没问题APPLIED原子落盘 + 记一条 UploadChunk + 累加 bytes_sent

落盘用「先写 .tmp 再 os.replace」（service.py:65），避免断电留下半个分片。写入和记库放在 transaction.atomic() 里，要么都成功要么都回滚。

5.5 按序合并（service.py:237）

with open(tmp_path, "wb") as out:
    for index in range(task.total_chunks):   # 严格 0 → n-1
        with open(_chunk_abs(task.file_hash, index), "rb") as fh:
            out.write(fh.read())

分片到达顺序完全不影响结果，因为顺序由编号决定，不由网络决定。演示里的「乱序分片」故意按 2, 0, 4, 1, 3 提交，合并出来仍与原文件逐字节相同。

5.6 二次校验、正式亮相、缩略图

合并完还要用 sha256_stream() 边读边算一次整文件指纹，和上传前声明的比对：

  • 不一致 → 删临时文件、任务标 failed、返回 CORRUPT，绝不入库；
  • 一致 → os.replace(tmp, final) 让文件正式可见 → get_or_create(FileRecord) → Pillow 生成 160×160 缩略图 → 删临时分片、保留 UploadChunk 记录（位图还要显示）。

这道「二次校验」不是多余的：每一片自己的指纹都能对上，但把别人的分片拼进来也是每片合法的，只有整文件指纹能抓出来。test_merge_rejects_wrong_whole_hash 就是专门伪造这种攻击的测试。

6. 三个卖点，分别落在哪几行代码

卖点专业说法落地位置
秒传内容寻址（content-addressable）：用内容指纹而不是文件名当身份service.py:88 查 FileRecord；命中后 bytes_sent=0
断点续传幂等记录 + 状态查询，客户端只补差集service.py:88 返回 uploaded；models.py:82 分片挂 file_hash；app.js:196 重新 check
乱序与并发编号即全序，服务端无状态接收service.py:169 按 index 落盘；service.py:237 按编号拼接；app.js:196 并发池

一个容易被忽略的点：秒传不是「跳过校验」。它跳过的只是字节传输，任务、事件、引用计数照样记录，看板上才有「0 字节」和「省下流量」可看。

7. 前端：Vue 3 看板与上传器

Django 模板和 Vue 的 {{ }} 撞车怎么办

Django 模板也用 {{ 变量 }}，Vue 也用 {{ 变量 }}。解决办法是把整个 #app 用 {% verbatim %} 包起来（templates/console.html），意思是「Django 别解析这一段，原样输出」，让 Vue 自己接管。代价是这一段里不能写 {% url %} 之类 Django 标签，所以接口地址在 app.js 里用字面量 /api/...。

Vue 管的状态

app.js 的 setup() 里用 ref 声明响应式状态（数据一变，界面自动重画）：state（看板数据）、picked（选中的文件）、progress、sent、phase、chunkStates（每片是 todo / doing / done / dup）、paused、interrupted、busy、notice。computed 负责派生值，比如 expectedTotal = ceil(文件大小 / 分片大小)。

界面适配

templates/base.html 里是一份自包含 CSS：CSS 变量定义浅色/深色两套配色，@media (prefers-color-scheme: dark) 自动跟随系统，@media (max-width: 520px) 把六列统计卡收成两列、按钮换行、表格放进 .table-wrap 横向滚动。手机端 500px 宽度已用无头浏览器截图核对过，没有横向溢出。

duplicate第 1 片连投两次第二次被 DUPLICATE 拦下，不重复写盘
resume先传 2 片，模拟断网，再新建任务补 3 片check 返回 uploaded=[0,1]，只补缺片
instant拿已存在档案的指纹再 check 一次0 字节、ref_count+1
all串起上面四个一次看清全貌

命令行也能跑：python manage.py demo_upload --scenario all，或 --scenario reset 清空。

「可观测性」（observability，系统把内部发生了什么讲清楚的能力）靠两张东西：UploadEvent 流水（每次检查/拦下/合并都留痕）和分片位图（灰=缺、绿=已到、紫=重复被拦）。没有这两样，重复被拦在页面上的数字会永远是 0，和项目 2 里踩过的坑一模一样。

12. 真实踩坑复盘

  1. 合并时临时文件被提前删掉。第一版用 try/finally 无条件删 .merging 临时文件，结果校验通过后还得重新拼一遍文件。改成「校验通过才 os.replace 正式亮相，失败才删临时文件」，代码短了一半，也讲得清。
  2. Django 模板缓存让 CSS 修复看不到。改完 base.html 后，运行中 --noreload 的服务仍返回旧模板，curl 抓到的 CSS 少一条规则。重启 runserver 后才生效——以后遇到「改了没反应」，先确认服务是否重新加载了模板。
  3. 暗色主题「记录」标签白底白字。.pill.muted 在浅色下是浅灰底，深色下必须单独覆盖背景与文字色，否则文字糊成一片。截图复核后确认修好。
  4. {% verbatim %} 与 Vue 模板冲突。不放进 verbatim，Django 会先把 {{ stats.files }} 当自己的变量解析掉，页面剩空白。
  5. 演示样本既要够大、又得是能出缩略图的图片。解决办法是用 Pillow 画一张 PNG，再往 IEND 之后追加确定性字节凑到目标大小；PNG 解码器忽略尾部数据，Pillow 仍能生成缩略图，而整文件指纹按完整字节流计算。
  6. CSRF cookie 从哪来。独立静态页做端到端测试时没有 csrftoken，先 fetch('/') 让 @ensure_csrf_cookie 种下 cookie，再发 POST 才通。
  7. 分片不能绑任务。早期思路把 UploadChunk 挂在 task_id 上，写续传逻辑时发现刷新页面后旧片全查不到，改成按 file_hash 共享（见第 4 节）。
  8. 别信前端报的片数。客户端可能算错或恶意伪造，total_chunks 一律由服务端按 size / chunk_size 重算；每片期望大小也由服务端算，最后一片才允许变小。

13. 想自己从零做出来，按这个顺序

  1. django-admin startproject 建骨架，startapp uploader，settings.py 配上 MEDIA_ROOT 和 SQLite。
  2. 先只写四张表 + python manage.py makemigrations && migrate。
  3. 写 hashing.py，用 python manage.py shell 手算一次 SHA-256，把「指纹」这个感觉建立起来。
  4. 写 service.py 的三个函数：check_upload → receive_chunk → merge_task，先不接 HTTP，直接在 shell 里传 bytes 调。
  5. 给这三个函数写测试（乱序、重复、缺片、伪造），测试过了再接 views.py。
  6. 接 7 个 URL，用 curl 或浏览器 DevTools 的 Network 面板看请求往返。
  7. 最后写 Vue 看板：先只做 /api/state/ 渲染，再加文件选择、切片、并发池、进度条、位图。

这个顺序就是「由外向内理解、由内向外实现」：先懂流程与骨架，再一点点添细节。

15. 上线前必须补的东西（诚实边界）

这个项目的目标是把原理讲清楚，不是生产级网盘。真要上线，至少还要：

  • 鉴权与隔离：现在所有文件全局共享，任何人算得出指纹就能引用；生产要按用户/租户隔离，并对秒传做权限校验。
  • 存储换成对象存储：本地磁盘不适合多机部署，分片应写 OSS/S3 并用服务端签发的直传凭证。
  • 增量哈希：现在浏览器 arrayBuffer() 把整个文件读进内存，几百 MB 还行，GB 级要改成按片增量计算或 Web Worker。
  • 过期清理：中断后没人续传的分片要定时回收，否则磁盘会涨。
  • 合并异步化：大文件合并应丢到后台任务队列，HTTP 请求立刻返回。
  • 限流与配额：限制单用户并发数、总容量、单片重试次数。
  • 指纹算法升级：SHA-256 足够教学用，但对「哈希碰撞导致误命中」零容忍的场景要加长度 + 采样二次校验。

把这些写进文档，比假装它们不存在更专业——面试时被追问，也能讲清楚边界在哪。

把一个文件切成 6 片之后，我才明白「秒传」不是魔法

项目 03 · 大文件分片上传与秒传 · 2026-11-16
技术栈：Django 5.2 + Vue 3 + Pillow + SQLite · 22 个测试

前两个项目做完之后，我一直想做一个「一眼能看懂在干什么」的后端项目。订单状态位图很硬核，但朋友点开看板，第一反应是「这些 0 和 1 是什么」。所以这次我选了大文件上传——每个人都被网盘里的「秒传」惊到过，原理却没那么玄。

结果真正动手，最先被教育的是我自己。

一、为什么不能一次 POST 上去

最朴素的上传就是：选文件 → 表单提交 → 服务端存下来。小文件没问题，文件一大就会同时撞上三堵墙：请求体太大被网关拒绝、传到 90% 断网要从头再来、一个慢连接把工作线程占住。

于是有了分片（chunk）：把文件按 2MB 切开，每片编号，分别上传。断网只重传那一块，多路并发还能更快。听起来简单，真正写起来第一件事就卡住了我。

二、我第一个版本犯的错：把分片绑在「任务」上

我建了一张 UploadChunk 表，字段是 task_id + index。写完上传、写完合并，一切正常。然后我加「断点续传」：模拟断网、刷新页面、重新选同一个文件——新任务查不到任何旧分片，只能从头传。

那一刻才明白：断点续传的本质不是「记住传到哪」，而是「让分片不属于某一次会话」。

改成用文件指纹 file_hash + index 当身份之后，逻辑突然变简单了：

uploaded = UploadChunk.objects.filter(file_hash=file_hash).values_list("index", flat=True)
# 返回给前端：这几片已经有了，只补剩下的

刷新页面、换个浏览器、甚至换个设备传同一个文件，都能接着传。这个改动只动了两个字段，但整个设计的重心从「追踪进度」变成了「记录事实」。

三、幂等不是 if 判断，是数据库说了算

分片重传太常见了：前端重试、用户手抖、并发池里两个 worker 抢到同一片。我第一版写的是：

if UploadChunk.objects.filter(...).exists():
    return "重复了"

本地单线程跑得好好的。但只要两个请求同时进来，两边都查到「不存在」，然后都去写盘——检查与写入之间有一道缝（术语叫竞态条件，race condition）。

正确的做法是把判断交给数据库：给 (file_hash, index) 加联合唯一约束（UniqueConstraint），写入和记库放进 transaction.atomic()，捕获 IntegrityError 当作重复投递。谁抢到谁写，没抢到的老实返回 DUPLICATE。

顺手把结果分成五种，页面上就讲得清了：APPLIED（落盘）、DUPLICATE（重复拦下）、CONFLICT（同编号不同内容，拒绝覆盖）、CORRUPT（片内容和它自己声明的指纹对不上）、REJECTED（编号或大小不对）。以前只返回一个「成功/失败」，出问题时完全不知道该查哪儿。

四、乱序一点都不可怕，因为顺序由编号决定

我做演示的时候故意把 5 片按 2, 0, 4, 1, 3 的顺序提交，想看看会不会翻车。结果合并函数里是这样写的：

for index in range(task.total_chunks):   # 严格 0 → n-1
    out.write(read_part(index))

它根本不关心谁先到，只按编号去取。这件事让我对「服务端无状态」有了具体的感觉：网络负责把东西送到，编号负责定义顺序，两件事解耦之后，并发和乱序都不用特殊处理。

反过来，如果我把顺序记在「到达时间的先后」上，就得维护一个脆弱的队列状态，一旦某个请求超时重排就全乱了。

五、秒传的本质：用内容当身份证

上传前浏览器先用 Web Crypto 算整文件的 SHA-256，服务端拿这串指纹去 FileRecord 表里查。查到了就直接复用，一个字节都不用传：

record = FileRecord.objects.filter(file_hash=file_hash).first()
if record:
    # 建任务、bytes_sent=0、ref_count+1、记一条 INSTANT 事件
    return {"instant": True, "saved_bytes": size}

专业说法叫内容寻址（content-addressable）：身份由内容决定，不由文件名决定。所以「把文件改个名字再传」照样秒传，「同名但内容改了一个字节」不会误命中。

有个细节我很喜欢：秒传跳过的只是「字节传输」，任务、事件、引用计数一个都不少。否则看板上「省下多少流量」这个数字就没地方来了。

六、每一片都对，不等于拼起来对

这是测试给我上的一课。

单片校验只检查「这一片内容和它自己声明的指纹是否一致」。假设我声明的是文件 A 的整文件指纹，实际却把文件 B 的 5 个分片（每片都带 B 的正确片指纹）传上去——每一片都能通过校验，缺片检查也能通过，合并出来的却是 B。

只有合并后对整文件再算一次 SHA-256，和上传前声明的比对，才能抓出来。所以合并函数里有两个动作：先按编号拼到 .merging 临时文件，算完指纹一致才 os.replace 让它「正式亮相」；不一致就删掉临时文件、任务标 failed、绝不入库。

我专门写了 test_merge_rejects_wrong_whole_hash 来伪造这种攻击。写完这个测试，才敢说「校验」两个字。

七、看不见的系统，等于没做对

第一版演示跑完，统计卡上的「重复拦下」永远是 0。我以为是幂等没生效，查了半天才发现：重复请求确实是拦下了，只是拦下之后直接 return，什么都没记。

这和项目 2 里踩过的坑一模一样。于是加了 UploadEvent 表：每次检查、每片到达、每次拦下、每次合并、每次整文件校验，都留一条流水；再用一串小方块画分片位图（灰=缺、绿=已到、紫=重复被拦）。

正确性靠约束，可解释性靠留痕，这是两套东西，得分开建表。加完之后，看板终于能自己讲清楚「刚才发生了什么」，我也不用再对着数据库猜。

八、让「一键演示」跑真链路，不造假数据

演示按钮我没有写成「往表里 insert 几条好看的记录」，而是让 run_demo_scenario() 在服务端老老实实调用 check_upload → receive_chunk → merge_task 这三个函数。四个场景分别制造：乱序到达、同一片重复投递、传两片后断网再续、同内容第二次上传。

好处是演示跑通 == 真实链路跑通；命令行 python manage.py demo_upload --scenario all 也是同一套代码，不开浏览器也能验证。写测试的时候更是省事：测试直接调 service 层，不用起服务器、不用管 CSRF。

为了位图好看，演示用 256KB 的小分片（5 片一眼数得清），浏览器真实上传仍是默认 2MB。服务端只按请求里声明的 chunk_size 算片数，两种尺寸天然共存——这也是「不写死参数」的小回报。

九、前端那些不大不小的坑

Vue 和 Django 抢 {{ }}。 两边模板语法一样，Django 会先把 Vue 的变量吃掉。把整个 #app 用 {% verbatim %} 包起来，Django 原样输出，Vue 才拿到完整模板。代价是这一段里不能再写 Django 标签，接口地址就写在 JS 里了。

不想装 npm。 把 vue.global.prod.js 放到 static/vendor/，一个 <script> 引完事。克隆仓库、装两个 Python 包、runserver，断网也能打开。

crypto.subtle 只在安全上下文可用。 本地必须访问 127.0.0.1 或 localhost，不能直接双击 HTML 文件。这个坑值得写进 README，不然换台电脑就懵。

改了 CSS 没反应。 我修暗色主题「记录」标签的白底白字，改完文件截图还是白底。用 curl 抓首页一看，返回的模板里根本没有新规则——--noreload 起的服务还抱着旧模板。重启服务，立刻好了。以后「改了没生效」，先查这一层。

并发池怎么写。 三个 worker 共享一个待传队列，queue.shift() 取下一片；暂停就是让 worker 在 while (paused) 里等，中断就是不再取新片（已在途的请求照常落盘，这才是真实断网）。写完发现核心代码不到 15 行。

十、最后跑了一遍真的

单元测试 22 个全过之后，我还是不太放心「浏览器那一段」——测试里的分片是 Python 构造的。于是用无头浏览器生成 1.3MB 文件，真的算指纹、真的切 6 片、真的 POST、真的合并、再传一次真的秒传，终端打出：

check: instant=false total=6
分片结果 APPLIED,APPLIED,APPLIED,APPLIED,APPLIED,APPLIED
merge: MERGED / 合并完成：6 片拼接，整文件指纹校验通过
二次上传 instant=true
RESULT OK

桌面 1280px 和手机 500px 各截了一张图，确认表格没溢出、暗色标签能看清。到这里才算敢说「做完了」。

十一、写在最后

这个项目最值钱的不是代码量（前后端加起来两千行出头），而是四个可以复用的判断：

  • 身份要挂在稳定不变的东西上（文件指纹，而不是会话 ID）；
  • 重复判断交给唯一约束，不要交给应用层 if；
  • 到达顺序不等于业务顺序，编号才是；
  • 局部正确不等于整体正确，收尾必须再做一次全局校验。

以及一条工程习惯：把内部发生了什么记下来。没有事件流水和位图，一个「跑通了」的系统和一个「其实什么都没做」的系统，在页面上看不出区别。

项目地址与文档都在仓库里，docs/technical-doc.md 是按「由外向内」写的技术文档，docs/reader.html 双击就能离线读。如果你也在学后端，建议先跑一遍 python manage.py demo_upload --scenario all，再对着事件时间线倒推每一步——比直接读代码容易多了。
