# 把一个文件切成 6 片之后，我才明白「秒传」不是魔法

> 项目 03 · 大文件分片上传与秒传 · 2026-11-16
> 技术栈：Django 5.2 + Vue 3 + Pillow + SQLite · 22 个测试

前两个项目做完之后，我一直想做一个「一眼能看懂在干什么」的后端项目。订单状态位图很硬核，但朋友点开看板，第一反应是「这些 0 和 1 是什么」。所以这次我选了大文件上传——每个人都被网盘里的「秒传」惊到过，原理却没那么玄。

结果真正动手，最先被教育的是我自己。

---

## 一、为什么不能一次 POST 上去

最朴素的上传就是：选文件 → 表单提交 → 服务端存下来。小文件没问题，文件一大就会同时撞上三堵墙：请求体太大被网关拒绝、传到 90% 断网要从头再来、一个慢连接把工作线程占住。

于是有了**分片**（chunk）：把文件按 2MB 切开，每片编号，分别上传。断网只重传那一块，多路并发还能更快。听起来简单，真正写起来第一件事就卡住了我。

---

## 二、我第一个版本犯的错：把分片绑在「任务」上

我建了一张 `UploadChunk` 表，字段是 `task_id + index`。写完上传、写完合并，一切正常。然后我加「断点续传」：模拟断网、刷新页面、重新选同一个文件——新任务查不到任何旧分片，只能从头传。

那一刻才明白：**断点续传的本质不是「记住传到哪」，而是「让分片不属于某一次会话」**。

改成用文件指纹 `file_hash + index` 当身份之后，逻辑突然变简单了：

```python
uploaded = UploadChunk.objects.filter(file_hash=file_hash).values_list("index", flat=True)
# 返回给前端：这几片已经有了，只补剩下的
```

刷新页面、换个浏览器、甚至换个设备传同一个文件，都能接着传。这个改动只动了两个字段，但整个设计的重心从「追踪进度」变成了「记录事实」。

---

## 三、幂等不是 `if` 判断，是数据库说了算

分片重传太常见了：前端重试、用户手抖、并发池里两个 worker 抢到同一片。我第一版写的是：

```python
if UploadChunk.objects.filter(...).exists():
    return "重复了"
```

本地单线程跑得好好的。但只要两个请求同时进来，两边都查到「不存在」，然后都去写盘——**检查与写入之间有一道缝**（术语叫竞态条件，race condition）。

正确的做法是把判断交给数据库：给 `(file_hash, index)` 加联合唯一约束（`UniqueConstraint`），写入和记库放进 `transaction.atomic()`，捕获 `IntegrityError` 当作重复投递。谁抢到谁写，没抢到的老实返回 `DUPLICATE`。

顺手把结果分成五种，页面上就讲得清了：`APPLIED`（落盘）、`DUPLICATE`（重复拦下）、`CONFLICT`（同编号不同内容，拒绝覆盖）、`CORRUPT`（片内容和它自己声明的指纹对不上）、`REJECTED`（编号或大小不对）。以前只返回一个「成功/失败」，出问题时完全不知道该查哪儿。

---

## 四、乱序一点都不可怕，因为顺序由编号决定

我做演示的时候故意把 5 片按 `2, 0, 4, 1, 3` 的顺序提交，想看看会不会翻车。结果合并函数里是这样写的：

```python
for index in range(task.total_chunks):   # 严格 0 → n-1
    out.write(read_part(index))
```

它根本不关心谁先到，只按编号去取。这件事让我对「服务端无状态」有了具体的感觉：**网络负责把东西送到，编号负责定义顺序**，两件事解耦之后，并发和乱序都不用特殊处理。

反过来，如果我把顺序记在「到达时间的先后」上，就得维护一个脆弱的队列状态，一旦某个请求超时重排就全乱了。

---

## 五、秒传的本质：用内容当身份证

上传前浏览器先用 Web Crypto 算整文件的 SHA-256，服务端拿这串指纹去 `FileRecord` 表里查。查到了就直接复用，一个字节都不用传：

```python
record = FileRecord.objects.filter(file_hash=file_hash).first()
if record:
    # 建任务、bytes_sent=0、ref_count+1、记一条 INSTANT 事件
    return {"instant": True, "saved_bytes": size}
```

专业说法叫**内容寻址**（content-addressable）：身份由内容决定，不由文件名决定。所以「把文件改个名字再传」照样秒传，「同名但内容改了一个字节」不会误命中。

有个细节我很喜欢：秒传跳过的只是「字节传输」，任务、事件、引用计数一个都不少。否则看板上「省下多少流量」这个数字就没地方来了。

---

## 六、每一片都对，不等于拼起来对

这是测试给我上的一课。

单片校验只检查「这一片内容和它自己声明的指纹是否一致」。假设我声明的是文件 A 的整文件指纹，实际却把文件 B 的 5 个分片（每片都带 B 的正确片指纹）传上去——每一片都能通过校验，缺片检查也能通过，合并出来的却是 B。

只有**合并后对整文件再算一次 SHA-256**，和上传前声明的比对，才能抓出来。所以合并函数里有两个动作：先按编号拼到 `.merging` 临时文件，算完指纹一致才 `os.replace` 让它「正式亮相」；不一致就删掉临时文件、任务标 `failed`、绝不入库。

我专门写了 `test_merge_rejects_wrong_whole_hash` 来伪造这种攻击。写完这个测试，才敢说「校验」两个字。

---

## 七、看不见的系统，等于没做对

第一版演示跑完，统计卡上的「重复拦下」永远是 0。我以为是幂等没生效，查了半天才发现：重复请求确实是拦下了，只是拦下之后直接 `return`，什么都没记。

这和项目 2 里踩过的坑一模一样。于是加了 `UploadEvent` 表：每次检查、每片到达、每次拦下、每次合并、每次整文件校验，都留一条流水；再用一串小方块画分片位图（灰=缺、绿=已到、紫=重复被拦）。

**正确性靠约束，可解释性靠留痕**，这是两套东西，得分开建表。加完之后，看板终于能自己讲清楚「刚才发生了什么」，我也不用再对着数据库猜。

---

## 八、让「一键演示」跑真链路，不造假数据

演示按钮我没有写成「往表里 insert 几条好看的记录」，而是让 `run_demo_scenario()` 在服务端老老实实调用 `check_upload → receive_chunk → merge_task` 这三个函数。四个场景分别制造：乱序到达、同一片重复投递、传两片后断网再续、同内容第二次上传。

好处是演示跑通 == 真实链路跑通；命令行 `python manage.py demo_upload --scenario all` 也是同一套代码，不开浏览器也能验证。写测试的时候更是省事：测试直接调 service 层，不用起服务器、不用管 CSRF。

为了位图好看，演示用 256KB 的小分片（5 片一眼数得清），浏览器真实上传仍是默认 2MB。服务端只按请求里声明的 `chunk_size` 算片数，两种尺寸天然共存——这也是「不写死参数」的小回报。

---

## 九、前端那些不大不小的坑

**Vue 和 Django 抢 `{{ }}`。** 两边模板语法一样，Django 会先把 Vue 的变量吃掉。把整个 `#app` 用 `{% verbatim %}` 包起来，Django 原样输出，Vue 才拿到完整模板。代价是这一段里不能再写 Django 标签，接口地址就写在 JS 里了。

**不想装 npm。** 把 `vue.global.prod.js` 放到 `static/vendor/`，一个 `<script>` 引完事。克隆仓库、装两个 Python 包、`runserver`，断网也能打开。

**`crypto.subtle` 只在安全上下文可用。** 本地必须访问 `127.0.0.1` 或 `localhost`，不能直接双击 HTML 文件。这个坑值得写进 README，不然换台电脑就懵。

**改了 CSS 没反应。** 我修暗色主题「记录」标签的白底白字，改完文件截图还是白底。用 `curl` 抓首页一看，返回的模板里根本没有新规则——`--noreload` 起的服务还抱着旧模板。重启服务，立刻好了。以后「改了没生效」，先查这一层。

**并发池怎么写。** 三个 worker 共享一个待传队列，`queue.shift()` 取下一片；暂停就是让 worker 在 `while (paused)` 里等，中断就是不再取新片（已在途的请求照常落盘，这才是真实断网）。写完发现核心代码不到 15 行。

## 十、最后跑了一遍真的

单元测试 22 个全过之后，我还是不太放心「浏览器那一段」——测试里的分片是 Python 构造的。于是用无头浏览器生成 1.3MB 文件，真的算指纹、真的切 6 片、真的 POST、真的合并、再传一次真的秒传，终端打出：

```text
check: instant=false total=6
分片结果 APPLIED,APPLIED,APPLIED,APPLIED,APPLIED,APPLIED
merge: MERGED / 合并完成：6 片拼接，整文件指纹校验通过
二次上传 instant=true
RESULT OK
```

桌面 1280px 和手机 500px 各截了一张图，确认表格没溢出、暗色标签能看清。到这里才算敢说「做完了」。

## 十一、写在最后

这个项目最值钱的不是代码量（前后端加起来两千行出头），而是四个可以复用的判断：

- **身份要挂在稳定不变的东西上**（文件指纹，而不是会话 ID）；
- **重复判断交给唯一约束**，不要交给应用层 `if`；
- **到达顺序不等于业务顺序**，编号才是；
- **局部正确不等于整体正确**，收尾必须再做一次全局校验。

以及一条工程习惯：**把内部发生了什么记下来**。没有事件流水和位图，一个「跑通了」的系统和一个「其实什么都没做」的系统，在页面上看不出区别。

项目地址与文档都在仓库里，`docs/technical-doc.md` 是按「由外向内」写的技术文档，`docs/reader.html` 双击就能离线读。如果你也在学后端，建议先跑一遍 `python manage.py demo_upload --scenario all`，再对着事件时间线倒推每一步——比直接读代码容易多了。
